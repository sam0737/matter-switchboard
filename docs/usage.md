# Usage

The `matter-switchboard` CLI manages the local service and calls its
administrator API over loopback HTTP. Remote programs use the user API over the
configured LAN IP and authenticate with scoped bearer keys.

Run `matter-switchboard --help` or `matter-switchboard <command> --help` for
complete flags and output formats.

Required arguments are prompted on a terminal. The setup code is not echoed.
A command that is not attached to a terminal exits if a required argument is
missing. Fabric removal also asks for the current fabric label on a terminal,
or takes `--confirm-fabric-label` when it is not.

## Administration

### Commission a device

The strip must already be connected to Wi-Fi and reachable on the same LAN as
the Switchboard host.

1. In an existing Matter admin such as Home Assistant, open the strip's
   multi-admin sharing/commissioning window.
2. Commission the strip. At a terminal, omit either argument to be prompted.
   The setup code is not echoed:

   ```sh
   matter-switchboard device commission
   matter-switchboard device commission patio-strip
   ```

   From a script, pass the slug and the setup code:

   ```sh
   matter-switchboard device commission patio-strip <code>
   ```

3. Switchboard commissions the strip onto its own Matter fabric and saves the
   controller and device state locally. No Wi-Fi credentials are requested or
   changed. Change the API name later with `matter-switchboard device rename`.

The original setup code is not used for multi-admin sharing. A new temporary
code must be generated by an existing administrator for each commissioning
session. The commissioning window expires; reopen it if it expires before
pairing finishes.

### List devices and endpoints

```sh
matter-switchboard device list
matter-switchboard device show patio-strip
matter-switchboard endpoint list patio-strip
```

The inventory includes slug, Matter Node ID, reachability, last successful
contact, and endpoint IDs/types reported by the device. Endpoint IDs are
device-specific; verify the outlet mapping before operating a new strip. Mock
devices are included and marked with `kind: mock`; they have endpoints 1 and 2
for their two sockets and do not have a Matter Node ID.

### Add and remove a mock strip

Mock strips are available in production as well as during development and
testing. They use the ordinary administrator CLI and do not need a physical
device or Matter commissioning window:

```sh
matter-switchboard mock add demo-strip
matter-switchboard mock list
matter-switchboard mock remove demo-strip
```

The mock has two socket endpoints, numbered 1 and 2. Their power states are
saved to disk and restored after a Switchboard restart. Removing a mock deletes
its inventory and saved state; it does not affect Matter fabrics or physical
devices. Mock outlets use the same control and power-state endpoints as real
outlets, so API clients can use either kind of device without changing their
request format.

### Ping/reachability

```sh
matter-switchboard device ping patio-strip
```

This performs Matter operational discovery and a secure read with a bounded
timeout. It reports `reachable`, `unreachable`, or `unknown`, plus the last
successful contact time and error detail. It is not an ICMP-only ping.

### Rename a device

```sh
matter-switchboard device rename patio-strip garage-strip
```

Slugs are unique, lowercase URL-safe identifiers. Renaming changes the API
address only; the Matter Node ID, fabric, and endpoints remain unchanged.

### Decommission this controller

```sh
matter-switchboard device decommission-self patio-strip
```

On a terminal, this asks you to type the device slug. It then asks the reachable
device to remove the Switchboard fabric and removes the local pairing and
inventory entry. Because the device removes the fabric used for the active
secure session, the session may close before a response is received; the CLI
verifies removal where possible and reports an indeterminate result distinctly
from success.

If the device is offline, remote decommissioning cannot be guaranteed. The
separate `matter-switchboard device forget-local patio-strip` command removes
only local inventory and credentials. On a terminal it asks you to type the
slug, and it warns that the fabric may remain on the device and consume a
fabric slot.

### Decommission another fabric

```sh
matter-switchboard fabric list patio-strip
matter-switchboard fabric remove patio-strip <fabric-index>
```

Removal displays the target fabric label and available vendor information,
then requires interactive confirmation. Non-interactive use requires
`--confirm-fabric-label <exact-label>`. A fabric with an empty label is
confirmed by typing its fabric index instead. Removing another Matter
administrator can disrupt that ecosystem's access. Fabric indices are local to
the device and can change; inspect the current fabric list immediately before
removing one. The target device must be reachable.

### Manage API keys

```sh
matter-switchboard key create automation-a control patio-strip garage-strip
matter-switchboard key create dashboard read
matter-switchboard key list
matter-switchboard key delete <name>
```

On a terminal, omit the name, scope, or devices to be prompted. Leave the
device prompt empty, or omit device arguments in a script, to allow every
device. Separate multiple slugs with spaces or commas.

`key delete` removes that key's record. The plaintext key is shown only when created. Store it in the calling
application's secret store. `read` keys can list devices/endpoints and read
state; `control` keys can also issue outlet commands. An optional device allow
list restricts a key to specific slugs. API keys cannot invoke administrator
operations.

## API usage

### Authentication and API discovery

Send the key in the HTTP authorization header:

```http
Authorization: Bearer <api-key>
```

Do not put credentials in a URL. The OpenAPI schema is at `/openapi.json` and
Swagger UI is at `/docs` on the configured API listener. The docs and health
check are open for inspection and are exempt from the API rate limit. Protected
operations still require authentication.

### List devices and endpoints

```http
GET /v1/devices
GET /v1/devices/{slug}
GET /v1/devices/{slug}/endpoints
```

The response includes stable slugs, Matter node IDs, endpoint IDs, endpoint
types, availability, and `lastSeen`. Power-strip outlets are represented as
endpoints under one device. Mock devices are marked `kind: mock`, have no
Matter Node ID, and expose socket endpoints 1 and 2.

### Turn an outlet on or off

```http
PUT /v1/devices/{slug}/endpoints/{endpointId}/power
Content-Type: application/json

{"on": true}
```

Set `on` to `false` to turn the outlet off. The operation is idempotent: repeat
requests set the same desired state. The response identifies the requested
action and reports the resulting observed state when available. Invalid slugs,
endpoints, or unsupported commands return a structured client error; unreachable
devices return a gateway/device error rather than claiming success.

Example:

```sh
curl -X PUT "http://192.168.1.40:8090/v1/devices/patio-strip/endpoints/2/power" \
  -H "Authorization: Bearer $MATTER_SWITCHBOARD_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"on":false}'
```

### Read state and electrical measurements

```http
GET /v1/devices/{slug}/endpoints/{endpointId}/state
```

The response reports the outlet power state and, when supported and exposed by
the device, current, voltage, and active power/wattage. Unsupported readings are
returned as `null` with a capability/status indicator; they are never presented
as zero. Mock sockets persist power state and return unsupported electrical
measurements as `null`. Each value includes or shares an `observedAt` timestamp
so callers can distinguish fresh data from cached data. A Matter write may
produce a new power state before the device reports electrical measurements.

### Reachability

```http
GET /v1/devices/{slug}/availability
```

Availability uses the controller's Matter discovery and secure communication
results, including the last successful check and any current error. A successful
HTTP response means the API handled the request; it does not itself mean the
strip is reachable.

### Rate-limit responses

Restricted routes are rate limited. Unauthenticated requests are limited to 3
requests per source IP per 5 seconds. Authenticated requests are limited to 30
requests per API key per 5 seconds. `/health`, `/openapi.json`, and `/docs` are
exempt. Exceeding a limit returns HTTP `429` and `Retry-After`. Outlet-specific
debounce/rate limits remain an open decision.
